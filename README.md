# Pick n Edge

A EuroLeague research tool with two areas, **Fantasy** and **Betting**, built on one shared data layer. Every statistic comes only from the official EuroLeague API (box score, play-by-play, shots, schedule, roster). The site reads ready-made files and never calls the EuroLeague API.

## Data flow

```
EuroLeague API ──(scripts/fetch)──▶ data/raw ──(scripts/build)──▶ data/clean ──(scripts/build/site-data.mjs)──▶ site/data ──▶ site/
```

- `data/raw/<season>/<game>/`: the exact API responses, gzipped and immutable (game, boxscore, playbyplay, shots), plus one roster and one schedule snapshot per season.
- `data/clean/`: one row per player-game and per team-game, plus shots and players. **Components only** (attempts, makes, rebounds, possessions on court, ...), never ratios.
- `site/data/`: precomputed Season / Last 10 / Last 5 / Last 3 views, `metrics.json`, `manifest.json`, per-game rows, shots by team, the roster and a copy of the metric engine. Generated; do not edit by hand.
- `site/`: static pages (one HTML file, ES modules, CSS). No build step.

## Theme and names

Colours and fonts live only in `site/theme/theme.json`, in two layers: **general colours** (what a colour means: page background, panel, line, accent...) and **component** entries (one per element and property). A component entry either points at a general colour, like `{semantic.panel}`, so changing the page background changes the card too, or holds a colour code (`#rrggbb` or `#rrggbbaa`) directly, which changes only that element. There is no palette to choose from: write the colour code where it is needed. `theme.css` is generated from the file (`node site/theme/generate.mjs`; a test fails if they differ), the style sheets and scripts only read variables, and a test fails if a raw colour, font or appearance-related inline style appears anywhere else.

**Appearance and layout are two files with the same names.** `theme.json` holds appearance: colours, font family, font size, corner radius, border width, shadow size. `config/sizes.json` holds layout: width, height, min/max, margin, padding, gap and position of every named element (`fantasy.player-card.tile.padding` there, `fantasy.player-card.tile.background` in the theme); it is generated into `config/sizes.css` with `node site/config/generate.mjs`. Where tiles sit on the card grid is still `config/layout.json` and the table column widths `config/table-layouts.json`. Tests fail if a raw colour, font, size or inline appearance shows up anywhere else (the few exceptions are listed at the top of `tests/theme/sizes.test.mjs`).

A component name reads **screen . component . part . property** in plain words, grouped by what you see: `fantasy.stat-table.header.background` is the background of the header of the Fantasy Players and Teams tables, `betting.stats-table.row-hover.background` the row under the mouse in the Betting statistics. The same name is the key in `theme.json` and the variable `--fantasy-stat-table-header-background`; the style sheets keep their class names, and `theme.css` ends with a list of which selectors read each name. To restyle something, name the element, find that key, change that one value.

The **name finder** (`site/theme/editor.html`, open it through any static server, e.g. `npx serve site` then `/theme/editor.html`) shows the real screens: click an element to see the names of its colours, appearance sizes and layout sizes, their current values, and the selectors that use them. It changes nothing; say the name and the new value in a chat, or edit that one entry in the file and run the generators. Sizes are plain values per element (`13px`, `4px 0`); there are no scales.

## The one rule for metrics

Every metric is defined **once**, in `scripts/metrics/registry.mjs`, as a numerator and a denominator over clean-table components, with a hand-checked unit test. A window (Season, Last N) sums the components over its games and then divides: ratios are never averages of per-game ratios. The site holds no formulas; it shows values from the views and `metrics.json`, and per-game values from the engine copy in `site/data/engine`. To add or fix a metric: change one registry entry, add its test, run the build.

## Run it locally

```bash
node scripts/build/build.mjs          # data/raw -> data/clean (prints a quality report)
node scripts/build/site-data.mjs      # data/clean -> site/data
node --test "tests/**/*.test.mjs"     # unit tests
npx serve site                        # open http://localhost:3000
```

Fetching new games needs network access: `node scripts/fetch/run.mjs --concurrency 1`.

## The update job

`.github/workflows/update-data.yml` is started by hand (`workflow_dispatch`; there is no cron yet).
- Normal run: fetch new finished games, rebuild `data/clean` and `site/data`, run the tests (nothing is committed if they fail), commit `data/` and `site/data/`, and start the Pages deploy. The deploy is started only on the default branch.
- `probe = true`: re-fetches 5 stored games, compares them byte for byte with `data/raw` and commits nothing. Use it to check that the API still answers and returns the same data.

## Manual data (`data/manual/`)

- `fantasy-position-overrides.json`: player positions that override the roster (G / F / C).
- `name-fixes.json`: display-name corrections.
- `eligibility.json`: display-only thresholds that decide which players the tables list (computed in the browser, never stored).
- `team-ids.json`: team code to logo id.

## The old site and what is deferred

The previous site is preserved by the tag **`old-site-final`** (last commit of the old site on `main`). To roll back, deploy that tag. The old Betting schedule page and its analysis (allowance, beneficiaries, rotation, absences, role shifts) are in that tag for the redesign.

Deferred or removed by decision: the Betting "From the schedule" page and the Tier 2 Betting analysis, Matchup, with/without teammate, NET PIR/USG, Value/CR, the custom window (to be designed as filters), and the players Charts mode (new charts to be designed).
